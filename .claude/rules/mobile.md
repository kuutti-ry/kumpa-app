# Mobile (Expo) rules

Stack: Expo SDK 57, React Native 0.86, React 19, TypeScript, dev client (`expo start --dev-client`, never Expo Go), web target for local runs only. UI: React Native Reusables on NativeWind v4. Use the Expo plugin's skills and MCP for SDK specifics, and check the installed SDK version before following any doc.

## Auth and network

- Backend-driven auth: open the system browser at `api/auth/start`, receive a one-time code by deep link, exchange it for a session. The link is the scheme's `kuutti://auth?code=…`, or the verified `https://<api>/auth/return?code=…` where the API serves the platform's file (ADR-074 §2); `app/+native-intent.ts` turns the second into the first's route (`signInReturnPath`), and nothing of either address is logged or sent to Sentry. The app never holds a client secret, an ID token, or Telia's PKCE state; it does hold its own verifier for each sign-in attempt, with the pending mark in `expo-secure-store`, whose SHA-256 `/auth/start` carries and `/auth/exchange` checks (RFC 8252 §8.1, ADR-027).
- Session and refresh tokens live in `expo-secure-store`, never AsyncStorage.
- App Attest (ADR-069): `src/lib/app-attest.ts` reaches Expo's `@expo/app-integrity` by its module's name (`requireOptionalNativeModule("ExpoAppIntegrity")`), never by an import, so the code runs in a build without the module; the dependency, pinned and never imported, and the App Attest entitlement are in the build since #184's native batch (ADR-074 §7). On an iPhone whose build holds it, the exchange carries Apple's attestation of a new key over the one-time code, and each refresh that key's assertion over the refresh token; the key's identifier is kept with the session. At the exchange every failure means nothing is sent: the app never refuses a sign-in for it, the API does where it requires one. At a refresh a key that is gone is refreshed without and the API ends the session, while a key that failed this once keeps the session and is tried again for a minute (`ASSERT_PATIENCE_MS`), never signed out for a hiccup. Every native call is bounded in time.
- API base URL comes from `Constants.expoConfig.hostUri` in dev and `EXPO_PUBLIC_API_URL` otherwise. `EXPO_PUBLIC_*` is public by definition; never put a secret there.
- No analytics or tracking SDK in the app.
- App Links and Universal Links files (`assetlinks.json`, `apple-app-site-association`) are served by the API, not bundled here. The app claims two paths on the API's four hosts, `/auth/return` and `/i/*` (`ios.associatedDomains`, `android.intentFilters` in `app.json`); `apps/api/src/identity/links.test.ts` holds `app.json` to what the API serves, so a host or a path changes in both. A link under `/i/` goes home and leaves its code, if it reads as one, on the phone for the code's field (`src/features/rewards/held-code.ts`, ADR-074 §4): never redeemed by itself, never logged.
- Random bytes come from `expo-crypto`'s `getRandomValues` (the sign-in verifier, the lock's salt; ADR-027 §5), never `Math.random` or a UUID. The clipboard is `expo-clipboard`.

## Images

- Upload only through the API. Pre-resize to 1600 px with `expo-image-manipulator` (which drops EXIF) before upload.
- Render with `expo-image`; `cacheKey` is `photoId/variant`, never the signed URL. Use the blurhash from the profile JSON as the placeholder.
- Variants: thumb in lists, card on open, full only on zoom. Never prefetch beyond the card on the screen; prefetch counts as exposure.
- Screenshots are never blocked (the maintainer's decision of 15/10/2026, #296): blind and partially sighted people describe a photo from a screenshot with Be My AI or Seeing AI, and TD-6's premise is that single-user capture cannot be prevented; the controls are the exposure budget and the fetch log (#52, ADR-008). Nor is a screenshot noticed, on either platform (ADR-056 §4): no `expo-screen-capture`, whose Android side announces every screenshot once it is linked.

## UI

- Tokens are CSS variables in `apps/mobile/src/theme/tokens.css`: four sets (light, dark, and the high-contrast pair) defined together, mapped to Tailwind names in `tailwind.config.js`; `userInterfaceStyle: automatic`, which `expo-system-ui` applies on Android (in the build since #184's native batch, never imported; ADR-074 §7). The designers' try adds Sini's four styles (Neobrutalism, Organic Pop, Glass, Bold Contrast; #408), each a light and a dark set, as classes ThemeProvider puts on the root view (chosen on the tech screen, so never in production; high contrast wins), named in full in `src/theme/looks.ts`, since Tailwind keeps a rule only for a class it finds written out. A primitive or a screen draws a style by its traits (`useLookTraits`), never by its name; high contrast drops Glass's see-through panes and every backdrop. A pressable whose words keep their colour when pressed (a row, a ghost or outlined control) fills with `pressFill(traits)`: today's `--accent`, a style's tint of its ink, since a style's `--accent` is a loud colour those words are not paired with (`src/theme/looks.test.ts` holds them on it). `--flourish` is a style's loudest colour, for its drawn shapes, never under words; a backdrop's tints are held by `src/components/backdrop.test.tsx` so that words keep 4.5:1 and lines 3:1 on them. `--stroke` is the ink of a control's or a container's outline and of its hard shadow: `useHardShadow` (`src/theme/shadow.ts`) draws it as React Native's own `boxShadow`, since NativeWind drops a shadow's offset, and NativeWind on a phone keeps only a variable some class uses. Never hardcode a colour: a component uses token classes (`bg-primary`, `text-muted-foreground`) only. A new token goes into all four sets and, if text sits on it, into the pair list of `src/theme/contrast.ts`; `pnpm --filter mobile check:contrast` holds text to 4.5:1 (7:1 in high contrast) and control outlines and the neighbours of the seeks bar to 3:1, in CI.
- Screens are built from the primitives in `src/components/ui/` (React Native Reusables, adapted; add one with `npx @react-native-reusables/cli add <name>` and then bring it to the baseline below). Wrap the app in `ThemeProvider`; test with `renderWithTheme` from `src/test/render.tsx`.
- The accessibility rules in `CLAUDE.md` apply to every component. Add `accessibilityLabel` and `accessibilityRole` in the same change that adds the touchable. The required-label convention: a primitive whose content is not plain text (`Button` with an icon child, `Input`, `Switch`, `DialogContent`'s `closeLabel`) takes its label as a required prop, so a missing label is a type error, and the string comes from i18n. Icons are decorative and hidden from screen readers.
- Sizes are minimums, never fixed heights (`min-h-touch`, 44 pt, `TOUCH_TARGET` in `src/theme/a11y.ts`); a control drawn smaller extends its target with `hitSlopFor`. Text scales with the OS up to `MAX_FONT_SCALE`, headings less (`HEADING_FONT_SCALE`), and a screen's title is `ScreenHeader`'s one line, shrinking to fit, so no word breaks in the middle (#467). A disabled or read-only control is drawn, never faded: no fill, a dashed `--input` outline, its label, icon or thumb in `--muted-foreground` (`Button`, `Input`, `Switch`, `Label`; #467). The enabled state says `border-solid`: on Android a border style that goes away keeps its dash (#548). `src/test/a11y.ts` (`pressables`, `a11yProblems`) checks role, label and target of everything pressable; run it over every new screen's tree.
- Every animation and haptic is gated by `useReducedMotion` / `useMotionDuration` / `useHapticTap` from `src/theme/`.
- Icons: one import per icon (`lucide-react-native/icons/<name>`), never the package root, which pulls the whole set into the bundle.
- Decisions are buttons with configurable placement (order, left or right thumb, one-handed): Like, Pass, the fish and Later. No swipe as primary input, no rapid repeat. The star is no decision: it sits on the card, and one-handed it comes down to the thumb's column with Undo (ADR-064).
- Every candidate card shows its reason label: matches all filters, liked you, sent you a fish (#378), seen before, or included because you relaxed X.
- The queue is one card at a time (`useQueue`), a page of `QUEUE_PAGE` read at a time, the next read only once the cards held are decided: never a list of people, a scroll or a "load more", and nothing fetched ahead of a decision. It ends: "That's everybody for now.", and nothing says to come back tomorrow (ADR-062 §1, §11). The Starred list (#575, ADR-064) is the one list of people, those the person chose themselves: short, in the order they starred them, signing nothing but a row's thumb, and a card opened from it is still one card at a time.
- Glyph sets never imitate console vendors' trademarked shapes or names. One exception, the maintainer's of 30/10/2026 (#520): Like and Pass may carry ✕ and ○, or A and B, as our own drawings in the text's colour, never more than these two shapes on a screen, and never a vendor's name, logo, colours or button artwork.
- Type (ADR-052 §4, #408): what is read, Kuutti's words and people's, is in the phone's own font, `font-system`, the `Text` primitive's default at 17 pt, as are `Input`, the dialog's description and a list's rows. Saiga, `font-sans`, draws headings, a button's words, labels, chips and the heading of a group of rows: the variants of `Text` (`h1` to `h4`, `title`, `group`, `small`), `Button`, `Label` and the dialog's title. Sizes come from the scale in `tailwind.config.js` (`text-h1` to `text-caption`, points on a phone), never Tailwind's rem sizes, which differ between a phone and the web. Saiga Regular is as dark as the system font's Semibold: a Saiga role names its weight (Regular, Medium for `h2` to `h4`, Bold for `h1` alone) and never `font-semibold`, which Saiga lacks and which is left to emphasis in the system font. Inside a `Button` its text class wins over a variant, so a row's words name `font-system` and their size themselves (`RowGroup`). Saiga has no tabular figures. A build or a web target without Saiga draws Saiga's text in the system font: a screen never depends on Saiga's metrics.
- The Android theme declares `android:forceDarkAllowed=false` (`plugins/withNoForceDark.js`, #27): the app follows the system scheme and ships its own dark and high-contrast sets, so a launcher's forced dark mode (MIUI) must not repaint them.
- It also declares `android:useBoundsForWidth=false` (`plugins/withAdvanceWidths.js`, #518): React Native 0.86 measures text by its glyphs' advances, and Android 15's TextView, by default for an app that targets API 35 or later, breaks lines by their ink, so a label sized to its own width lost its last word. Remove it only once React Native measures by the ink too.

## Notifications

- Three pushes, and no daily one (ADR-062 §12): a message, to somebody not in the app, at most once a conversation per `message_push_min_interval_minutes`; a new match, to the person whose earlier like it met (both the maintainer's of 25/10/2026); and an announcement to everybody whose notice of it is unread, which a tap opens on home (#573, ADR-068 §4, his of 07/11/2026). Nothing in the quiet hours. A push says that there is something, never what or from whom: no message text, no name, no account id, no badge (ADR-055).
- The permission is asked once there is something to tell (the home screen's offer, once matching is open), with the reason, never at the first start; an answer is remembered and the offer never comes back. Everything works without it.

## i18n

- Every user-facing string is a typed `t()` key from `packages/i18n`, through `useT()` from `src/lib/locale.tsx`. No inline strings (`pnpm lint` fails on them), no concatenation with inflected values; `in {pond}` is banned. Required label props (`accessibilityLabel`, `closeLabel`) take `t(...)` too.
- The language is the stored in-app choice if there is one, else the phone's first language with a catalogue (`expo-localization`), else English; `LocaleProvider` wraps the app above `ThemeProvider`. Tests render through `renderWithTheme`, which supplies both, and set the phone's language with the `expo-localization` mock (`src/lib/locale.test.tsx`).
- ICU plurals; Intl for dates and numbers; the `en-XA` pseudo-locale in dev builds to catch overflow.

## Testing and builds

- Component tests use jest-expo, not Vitest. Test that accessibility props exist.
- A change to a screen is walked with VoiceOver and TalkBack before it is pushed (#217): no unlabelled control, no path that only a gesture opens, and the pull request says which screens were walked, on which phones, by whom. A screen or step added or removed adds or removes its row in `docs/accessibility-checklist.md`, the chart of the pass before each release. An agent cannot run a screen reader, and a jest check, a screenshot or a read of the code is no walk: it pushes the screen unwalked, its pull request says so and why, and its commit message carries a line `Unwalked: <screens>`, which the squash keeps on `main`. Such a pull request merges when green like any other (the maintainer, 17/10/2026); the release pass walks those screens first (`git log <last tag>..origin/main --grep '^Unwalked:'`). A walk not done is never claimed.
- EAS Update uses `runtimeVersion: { policy: "fingerprint" }`; rebuild natively only when the fingerprint changes. Channels `staging` and `production` follow the deploy promotion. Any change to `app.json` moves the fingerprint of both platforms and orphans every installed build; batch native changes. `app.config.ts` stamps the git commit into `extra.commit`, and `fingerprint.config.js` skips `extra` so that a commit is never a native change. It also leaves `eas.json` out, so that a profile or a submission is never one either; `plugins/fingerprint.test.js` refuses a build profile with `env`, `prebuildCommand` or `config`, which would make it native again (ADR-057).
- The web target runs only on a developer's machine, against the local API, the mock bank and seed data (`pnpm env:up`), and is never deployed (ADR-070). Nothing in the web target may become a product web surface.

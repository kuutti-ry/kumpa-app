# ADR-076: The audit log keeps five years, then the night deletes a row

- Status: proposed (#714, built as written here, §6 on the security review's findings of 2026-11-18; the five years are TD-7's and ADR-006 §6's, as the privacy policy in force says them, and this record decides only how they are kept; the deploy that carries it needs the owner script's `release` before it and the script again after, on staging and on production, which are the maintainer's, §5; accepting it is the maintainer's)
- Date: 2026-11-18
- Follows: TD-7 (what erasure keeps: the audit log's rows, for five years), TD-5 (the audit log), ADR-006 §6 (the table append-only by its trigger, and the role boundary that keeps the trigger out of the application's hands), ADR-007 (the audit log is not touched by erasure), CLAUDE.md rule 10 (a custom migration for what the schema DSL cannot express), `.claude/rules/db.md`, issue #714; amends ADR-006 §6

## Context

The privacy policy in force (`2026-11-1`, on the site) says the record of what moderators and admins did is kept five years, as TD-7 and ADR-006 §6 decided. Nothing deleted a row of `audit_log`, and by ADR-006 §6's design nothing could: the trigger refused every UPDATE, DELETE and TRUNCATE from anybody, the table's owner included, and the table, its trigger function and the `public` schema belong to `kuutti_audit`, a role the API never connects as, so `kuutti_app` holds SELECT and INSERT alone and can neither disable the trigger nor replace its function. A row was therefore kept for good. The first row is from October 2026, so none is five years old before October 2031. The texts of 16/11/2026 found the gap (#190); the maintainer's disposition of 17/11/2026 kept the record as it stood, with a `shortcut:` note on the nightly jobs naming the ceiling, and opened #714 for the deletion.

What the deletion must not do is give the application role a way to delete the rows it should not: the point of the boundary is that a compromised API cannot remove the record of what staff did.

## Decision

1. **The trigger keeps five years, then lets a row go.** `audit_log_immutable()` lets the DELETE of a row through when the row was written more than five years ago (`at < now() - interval '5 years'`), and refuses every other change as before: any UPDATE, old rows included; any DELETE of a younger row, whoever asks; any TRUNCATE, which a statement trigger refuses without asking an age. A statement that reaches one row younger than five years fails whole. A row of exactly five years is kept until the next night.
2. **One function deletes, and the application calls it.** `audit_log_prune()` deletes exactly the rows past five years and answers how many. It is `SECURITY DEFINER`: owned by `kuutti_audit`, it runs as the table's owner, which alone holds DELETE. It takes no argument, so a caller cannot widen it. It carries its own `search_path` (`pg_catalog, pg_temp`) and time zone (UTC), and so does the trigger function: the application role owns the database and may create a schema, open it to everybody and put a function of its own named `now` before `pg_catalog` on its path, which would otherwise move both lines to infinity and let every row go (`packages/db/src/audit-owner.test.ts` does exactly that and shows it moves nothing); a session's time zone would otherwise move the line by up to an hour. `now()` is the transaction's start on the database's clock, the same instant for the function's predicate and the trigger's, and never the API's clock. The migration takes EXECUTE from PUBLIC; the owner script hands the function to `kuutti_audit` with the table and grants EXECUTE to `kuutti_app`, and the release script hands it back with them. So a deployed database holds the line twice: the application role cannot delete a row itself, nor change the one statement it may run, and that statement, if it were ever wrong, still meets the trigger.
3. **The night calls it.** The nightly job `prune-audit-log` (`pruneAuditLog`, `apps/api/src/safety/audit.ts`) runs after `prune-reports`, its count in the job's log line. Nothing else calls the function.
4. **What ADR-006 §6's guarantee becomes.** No row of `public.audit_log` can be rewritten or dropped by the application connection, and none removed before it is five years old; after five years the night removes it. A row's `at` is what its insert wrote: the API never sets it (the column's default, the insert's own time), and a credential that can INSERT could write a row dated in the past, which the next night deletes; that removes only what it forged, which it could have written anyway. The same credential could write a row dated in the future, which no night would reach, a row it could equally have written today; this record accepts that, as no route of the API sets `at`. A check that `at` is not in the future is the way to close it, should one ever be wanted.
5. **Deploying it.** The migration (`packages/db/drizzle/0014_audit_log_prune.sql`) replaces a function `kuutti_audit` owns, so as `kuutti_app` it fails, and with it the boot, the migrations before it applied (ADR-075), until ownership is handed back: on each of staging and production, `infra/scripts/db-audit-owner.sh <env> release`, the deploy, then `infra/scripts/db-audit-owner.sh <env>` (infra/README.md). Until the last step the boot warns that the boundary is not enforced, as after any release.

6. **The owner script takes back only what the migrations made.** While a release hands the table and its two functions to `kuutti_app`, the application role may add to them, and before this record that was harmless once the owner script ran: nothing ever ran in `kuutti_audit`'s hands. The prune changes that. Its DELETE fires every trigger on the table as the owner, a statement trigger even when no row is old, and the owner's ANALYZE evaluates an index's expressions, so what a release added would run as `kuutti_audit` every night, able to replace the trigger function and delete any row (the security review of #714 showed it with a planted trigger and with a planted `search_path`). So `infra/scripts/db-audit-owner.sql` first computes the shape of `audit_log` and its two functions: the table's kind, persistence and row security, its columns with their types and defaults, its constraints and those that point at it, its indexes, triggers, rules, policies, inheritance and statistics, and each function's whole definition, its body, `SECURITY DEFINER` and settings included. Owners, grants and whether the triggers are enabled stay out, as the script sets them. Unless the shape's SHA-256 is the one the migrations leave on a fresh database, the script refuses with the shape in its detail and hands nothing over, so the table stays the application role's and the boot keeps warning. `packages/db/src/audit-owner.test.ts` holds the hash to a fresh database and plants each kind of addition during a release to see it refused. A migration that changes the table or its functions writes the new hash into the script in the same pull request. What a release granted outlasts it too, since an owner's grants pass to the next owner: TRIGGER or REFERENCES left to PUBLIC, to `pg_database_owner`, whose one member is the application role, or on a column alone would let it add, once the table is back, a trigger the prune runs as the owner, or a foreign key that blocks the prune. So the script then takes every grant on the table, its columns and both functions from everybody but the owner, gives the owner its own back in full, and grants `kuutti_app` SELECT and INSERT on the table and EXECUTE on the prune, and nothing more; the boot's check counts TRIGGER and REFERENCES, on the table or on a column, as a way around the boundary. And the application role owns the database, so without any release it may give every session there a search path with the public schema first, and it may always create functions in that schema: one with a catalog function's name, or one that fits an unquoted literal better than the catalog's, would then run in the master's hands in either script. Both scripts set the catalog alone as their first statement, and `db-audit-owner.sh` sets it at connection too (the review's second pass showed all three ways, the last two needing no release).

## Consequences

- From October 2031 each night deletes the rows that turned five that day, and the privacy policy's five years hold as written. The lines of the police-disclosure runbook and of the register that said the rows were kept longer no longer apply.
- The prune reads the table whole: there is no index on `at` alone. The staff's log is thousands of rows a year, not the hundreds of millions of `photo_access`, whose prune needed one (ADR-008 History 16/11/2026); an index comes with a migration if the night's time ever shows the need.
- The boot's boundary check counts TRIGGER and REFERENCES now (§6) and is otherwise unchanged. The prune's owner is not part of it: a prune that `kuutti_app` owned on a table `kuutti_audit` owns would run without DELETE and fail in the night's log, deleting nothing. A table the owner script refused (§6) stays the application role's, which the check already reports as not enforced. The script refuses a database the migration has not reached the same way, before it hands anything over.
- The shape check also closes what was open before this record, unnoticed: an index with an expression added during a release, evaluated by the owner's ANALYZE, or a table made UNLOGGED, which a crash would empty.
- The shape's text is PostgreSQL's own rendering of the definitions, stable within a major version and nearly always across its minor releases, which RDS applies by itself. A database whose history made it differ from a fresh one in a way that does not matter, or an upgrade to PostgreSQL 18, makes the script refuse until the difference is read and the hash written anew.
- MAINTAIN, which PostgreSQL 17 adds, goes with every other grant but is not counted at boot: with no expression left on the table it allows LOCK, VACUUM and ANALYZE, which can stall the API but reach no row, and the local environment may still run PostgreSQL 16, where the check could not name it.
- The application role may still make a `public.audit_log_prune(integer DEFAULT 0)` beside the real one, which makes the night's call ambiguous: the night fails in its log and rows are kept longer, as a compromised API could have them kept by not calling the prune at all.
- The superuser and the RDS master role, as a member of `kuutti_audit`, could still disable the trigger, as ADR-006 §6 says; the trigger now holds them to five years only while it is enabled.

## Alternatives considered

**The function disabling the trigger for its own transaction** (`ALTER TABLE ... DISABLE TRIGGER`, the delete, `ENABLE ALWAYS` again): no change to the trigger and no release around the deploy, only the owner script after it. Rejected: the table's own rule would still say never while one function said otherwise, the trigger would no longer hold anybody to five years, and a mistake in the function's predicate would meet nothing.

**DELETE granted to the application role, the trigger's age the only rule.** No function, one statement from the night. Rejected: one line where the function gives two, and the boot's check, which refuses a DELETE grant, would have to accept one.

**The trigger telling the function's delete from others** by a setting the function sets, or by `current_user`: any session can set a custom setting, and only the owner holds DELETE anyway, so neither gates anything the privilege does not.

**A tunable in `matching_config`.** Rejected: the five years are a rule of the privacy policy, not a product tunable, and a row the application role can write would let it move the line.
